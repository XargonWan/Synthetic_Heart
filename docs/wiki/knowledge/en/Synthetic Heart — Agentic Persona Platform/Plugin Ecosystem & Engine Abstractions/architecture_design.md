The module is organized into two layers. The top-level base classes (`auris_base.py`, `iris_base.py`, `vox_base.py`, `live_base.py`) define abstract interfaces for pluggable engines: each declares a `display_name`, an abstract core method (`transcribe`, `describe_image`, `generate_tts`, or the async session lifecycle), optional `setup`/`teardown` hooks, and a registration pattern where subclasses set `ENGINE_CLASS` and call a registry function from `core.*_registry` at import time. Concrete engine implementations live in sibling sub-packages (`auris_engines/vosk_engine.py`, `live_engines/gemini.py`, `vox_engines/http.py`, `vox_engines/kitten.py`).

Feature plugins each follow a uniform shape: a directory with `__init__.py`, `<name>.py` (or a nested package like `grillo/` and `rift_vessel/`), and a `<name>.guide.md` documentation file. Plugins register themselves via `core.core_initializer.register_plugin(name, self)` during `__init__`, expose capabilities through `get_supported_action_types` / `get_supported_actions` / `get_prompt_instructions`, and implement `execute_action` (sync or async). Some plugins extend `AIPluginBase` (`agent_plugin`, `grillo/grillo_impl.py`, `rift_vessel/vessel_plugin.py`) while others are plain classes (`web_search_plugin`, `radio_host/radio_host_plugin.py`). Backward compatibility is maintained via thin wrappers like `plugins/grillo_plugin.py` that re-export `PLUGIN_CLASS` from the new location.

Dependency direction is one-way: plugins depend on `core.*` registries/config/logging but never on each other directly; cross-plugin interaction happens through the central `PLUGIN_REGISTRY` (e.g., Grillo discovers optional beat plugins by scanning it).
