Each file defines a self-contained plugin class that conforms to one of two patterns used by the core plugin system: (1) subclasses `core.plugin_base.PluginBase` and exposes `get_supported_actions`, `get_supported_action_types`, and optional `static_inject` hooks (e.g. `gasmask.py`), or (2) implements the standard action interface with `get_supported_action_types`, `get_supported_actions`, `get_prompt_instructions`, `execute_action`, and optionally `handle_custom_action`, then registers itself via `register_plugin(name, instance)` in `__init__` (e.g. `selenium_elevenlabs.py`, `terminal.py`, `reddit_plugin.py`). Discovery is driven by a module-level `PLUGIN_CLASS` attribute exported by each file, which `core.core_initializer` uses for auto-discovery. Plugins are gated behind the `dev_components` flag so they never persist into production. Cross-cutting concerns (logging, config, notifier, validation registry, interface registry) are imported from `core.*` modules; optional dependencies like `telegram` or `core.notifier` are wrapped in try/except fallbacks to keep tests runnable without them.
