Four cooperating modules form a pipeline: `prompt_request.py` defines the immutable dataclasses (`Turn`, `RuntimeContext`, `Attachment`, `PromptRequest`) that serve as the single intermediate representation between prompt builders and LLM engines. `prompt_engine.py` is the heavy builder — it parses history strings into `Turn` objects, merges memories/thoughts/diary entries into a `context_summary`, computes per-turn action scopes, handles attachment text extraction (PDF pages, AcroForm fields, textual previews), and produces the `PromptRequest`. `prompt_renderers.py` contains pure, stateless renderer classes (`OpenAIRenderer`, `AnthropicRenderer`, `GeminiRenderer`, `TextRenderer`, `LiveRenderer`) that each consume a `PromptRequest` and emit the native wire format for their target API, with shared helpers like `_build_runtime_prefix` and `_manifest_to_*_tool` converting `ToolManifest` objects to provider schemas. `variables_engine.py` provides a separate but related subsystem: an `ExposedVariableRegistry` with typed `ExposedVarDefinition`s, validation (type casts, regex, min/max/choices), and registration of all UI-exposed configuration keys via `register_exposed_var()` calls in `register_all()`, which delegates persistence to `config_registry`. Dependency direction is one-way: renderers depend on `PromptRequest`; the engine depends on renderers only indirectly; variables_engine depends only on `config_registry` and logging utilities.
