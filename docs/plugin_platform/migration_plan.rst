H. Migration Plan
=================

The sequence follows the **actual coupling** found in :doc:`dependency_analysis`,
not the order of the brief. Each milestone is small and independently testable.
Nothing here is implemented; implementation happens in later sessions.

Principles
----------

* **No legacy or compatibility layer.** The platform carries no adapter for old
  in-process plugins and no coexistence mode. Every first-party plugin lives in
  this repository and is rewritten (or deleted) when its turn comes; third-party
  plugins are rewritten by their authors against the extension API. The old
  scans keep working only until the code they load is migrated, and are then
  removed together with it.
* One runtime path: the extension process behind the gateway.
* No data loss: existing chat history, interface paths and aliases keep
  resolving. An interface that changes its path scheme ships its own data
  migration (precedent: ``core/migrations.py``).
* Telegram is the **first migration case**, not the design centre. The generic
  contract must not be shaped like Telegram; a second, differently shaped
  interface validates it.
* When code that someone may later need is deleted, commit the deletion on its
  own and leave a comment naming the commit hash and the
  ``git log --diff-filter=D -- <path>`` command (``CLAUDE.md`` rule).

Critical risk: Telegram
-----------------------

* 30 and 35 distinct ``core`` imports, 123 string references in 37 files, 122
  test files with a ``telegram_bot`` fixture string.
* Mitigation: two phases (M4 out of process in-tree, M5 extraction), M0
  characterisation tests, a second interface validating the contract, and an
  acceptance check by search (``rg -i telegram core/``).
* If M3 reveals the API cannot express a Telegram need, the response is a new
  API, not a shortcut.

Post-update step (done, 2026-11-25)
-----------------------------------

An update must not leave a working install without the interfaces it used, and must not
ask the person to install extensions by hand. At the end of the milestones, a post-update
step works out which old components the user really uses and downloads the extensions
that replace them:

* **skip** components that are not configured with their *mandatory* settings (they do
  not work today either) and those that are switched off;
* **evaluate case by case** those that only have default settings (do not assume);
* **take over** the user's settings: the old ``TELEGRAM_*`` keys become the new
  extension's keys, and a stored user-account session becomes the extension's own
  storage, so nobody has to log in again.

**Implemented** in ``core/extensions/legacy.py`` (the decisions, pure) and
``legacy_port.py`` (the Core side), run once from the extension start-up after the
first-start defaults (``State.legacy_done``; a database that cannot be read is retried at
the next start):

.. list-table::
   :header-rows: 1
   :widths: 24 76

   * - Old component
     - What happens
   * - ``telegram_bot``
     - ``BOTFATHER_TOKEN`` is copied to ``official/telegram_bot`` if it was set; with no
       token it never worked and nothing is copied. ``INTERFACE_ENABLED__telegram_bot``
       false: the extension is installed (it is a default) but switched off.
   * - ``telegram`` (userbot)
     - Only if ``TELEGRAM_API_ID``, ``TELEGRAM_API_HASH`` and a ``TELEGRAM_SESSION`` were
       all there **and** it was not switched off: ``official/telegram`` is installed from a
       trusted repository (it is not in the image: 162 MB), granted what it declares, its
       ``TELEGRAM_*`` settings are copied and the login session goes into the extension's
       storage, so nobody logs in again. If no repository offers it the log says to
       install it from Plugins > Store and the settings are picked up (there is no hosted
       official repository yet).
   * - ``fluxer_bot``
     - ``FLUXER_*`` copied if a token was set; switched off stays off.
   * - ``ollama_serve``
     - It ran without any setting, so ``official/openai_api`` stays on unless
       ``OLLAMA_SERVER_ENABLED`` or ``INTERFACE_ENABLED__ollama_serve`` was false.
       ``OLLAMA_MAX_HISTORY``, ``OLLAMA_COMPLETION_TIMEOUT`` and ``OLLAMA_HOST`` become
       ``OPENAI_API_MAX_HISTORY``, ``OPENAI_API_TIMEOUT`` and ``OPENAI_API_HOST``; the
       other ``OLLAMA_*`` keys are dropped.

A value the extension already holds that differs from its default is never overwritten, a
login session already stored is never replaced, and one component failing does not stop
the others. The result is logged (``[extensions] settings of the old plugins: ...``).
**Not run against a real database or a real old installation**; the logic, the adapter and
the once-only start-up are covered by ``tests/test_extensions_legacy.py``.

Data continuity (no code compatibility)
---------------------------------------

The platform keeps no compatibility code for old plugins (see Principles). What
it does keep is the user's **data**:

* Existing configuration keys (``PLUGIN_ENABLED__*``, ``INTERFACE_ENABLED__*``,
  ``OLLAMA_*``, ``ZEN_*``) are migrated by ``core/migrations.py`` when an
  extension takes ownership of them.
* An existing install keeps its endpoints and its default extensions:
  ``default_install`` applies to **fresh** installs; upgrades install the
  extensions that replace removed Core code so behaviour does not change.
* ``interface_paths``/``chat_history_cache``/``interface_aliases`` are not
  altered by the platform itself.
